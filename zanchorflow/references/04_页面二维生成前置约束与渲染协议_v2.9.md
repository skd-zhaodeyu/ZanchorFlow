# 页面二维生成前置约束与渲染协议 v2.9
## Pre-Generation 2D Design & Rendering Protocol

**适用范围：** PPT 图片页面实际调用生图模型之前的二维合法化、正向渲染引导与 Preflight，以及生成后的最低必要资格审核。  
**核心目标：** 在图像生成发生之前排除 Isometric、Axonometric、2.5D、Pseudo-3D、以实体体积或三维空间模拟为主要视觉机制的场景、照片感 / 摄影素材感、HUD Glow 等错误视觉方向；同时允许正常二维插画中的有限空间线索。生成后只判断是否存在足以阻止正式使用的明确缺陷，避免把审核变成无限审美优化循环。  
**职责边界：** 本文件不决定页面语义、不决定候选风格、不提炼 Anchor，也不决定页面应该采用流程图、系统图、图表还是插画。这些由上游《PPT视觉探索与Anchor延续协议》完成。

---

# 1. 核心原则

## Rule 1 — Pre-generation control first

> Do not use image generation as the visual-planning stage.

应先在文本阶段把视觉方向规划正确，再调用生图模型。

如果方案本身依赖系统性的三维透视、实体厚度、照片感主视觉、HUD 或伪3D才能成立，应在生成前重新规划，而不是先生成再修。正常二维插画为表达空间关系而使用的有限遮挡、远近或轻微透视线索，不因此自动触发 RE-PLAN。

## Rule 2 — Positive definition first

先明确“应该怎样画”，再补充禁止项。

正式 Prompt 顺序应优先描述：

- 上游已经选定的 `primary_visual_carrier` 与具体表达机制；
- 如何把该既定方案渲染为明显二维、非照片化的页面；
- 与上游方案相符的二维视觉语言；它可以是扁平插画、编辑型插画、图解、信息设计、技术线稿、数据视觉、平面几何构成或其他合法二维形式，但不存在本协议预设的默认媒介；
- 只对真正违反当前二维 / 非照片化边界的局部机制做最小合法化，不重选页面视觉方案。

之后再补充 Isometric、Pseudo-3D、照片感、HUD、Glow 等禁止项。

## Rule 3 — 2D is a rendering boundary, not a creative template

二维协议只约束视觉合法性，不替上游设计页面。

禁止因为“必须二维”就把所有页面统一退化成：

- 图标墙；
- 四宫格；
- 简单卡片；
- 儿童式扁平插画；
- 单一线性流程。

## Rule 4 — 2D does not mean simplistic

允许：

- 高信息密度二维系统图；
- 复杂但清晰的二维工程线稿；
- 高级编辑构图；
- 精细数据可视化；
- 多层二维关系；
- 专业二维插画。

Flat 2D 约束不等于降低专业度和视觉复杂度。

## Rule 5 — Graphic, not photographic

页面主视觉应呈现为**经过设计的二维图形语言**，而不是“被相机拍摄出来”或“以写实渲染模拟照片”的场景。

本协议同时要求：

> **DEFAULT: FLAT_2D + NON-PHOTOGRAPHIC RENDERING**
>
> **OPTIONAL EXPLICIT MODE: ZERO_PERSPECTIVE_2D**

二者是相互独立的边界：

- 一个画面可以完全二维，但仍然具有强烈照片感；
- 一个画面也可以不是照片，却通过透视、体积和材质模拟形成伪3D。

因此默认必须同时满足 Flat 2D 与非照片化；只有上游明确冻结 `ZERO_PERSPECTIVE_2D` 时，才额外禁止普通二维插画中原本可以接受的局部空间线索。

## Rule 6 — Qualification, not unbounded optimization

生成后审核的目标是判断页面是否**达到正式使用资格**，不是继续寻找理论上的更优视觉结果。

核心问题必须是：

> **Is there a concrete reason this image cannot be used?**

而不是：

> Can this image still be improved?

因此：

- `PASS` 是不存在明确 Hard Failure 时的默认结论；
- `REVISE / REJECT` 必须能够指向本协议定义的 Hard Gate，并给出可观察证据；
- Soft Preference 不得单独或累计触发自动重生；
- 页面一旦 PASS，应停止该页的自动生成，除非用户明确要求继续尝试。

# 2. 输入接口

文件 B 接收上游已经解决好的页面设计信息。

无论 Exploration Generation 还是 Anchored Production，文件 B 均同时接收上游已确定的 `page_goal / resolved semantics`、`mandatory_information`、`semantic_relation` 和 `acceptance_criteria`。这些语义与强制信息由 Stage 1 → Stage 2 接口的六字段语义契约编译得到；下列结构只描述各模式新增的视觉计划字段，不替代上述语义输入。

可能是：

## Exploration Generation

```yaml
design_concept:
  semantic_strategy:
  primary_visual_carrier:
  composition_idea:
  information_grouping:
  visual_rhythm:
  color_direction:
```

## Anchored Production

```yaml
production_visual_plan:
  page_goal:
  semantic_relation:
  selected_visual_form:
  composition_concept:
  information_hierarchy:
  relevant_style_dna:
```

本协议不得重新解释或改写这些语义关系。

在 Exploration Generation 中，`color_direction` 属于上游已经确定的候选设计信息。除非它与可读性、强制信息或全局渲染边界发生冲突，本协议应保留该色彩方向，不得在二维合法化或 Prompt 编译时自动归一化为某种默认“科技色”或行业惯用配色。

如果上游方案在当前二维渲染模式、非照片化条件下无法成立：

> 返回 RE-PLAN，而不是自行改变语义。


## 2.1 Rendering Mode

二维渲染模式只有两个：

```yaml
rendering_protocol:
  mode: FLAT_2D  # default
```

或在上游存在明确冻结依据时：

```yaml
rendering_protocol:
  mode: ZERO_PERSPECTIVE_2D
```

`FLAT_2D` 是默认模式。`ZERO_PERSPECTIVE_2D` 只能来自用户明确要求、任务明确规范或既有正式视觉规范；不得由 Anchor 恰好无透视、某一候选采用正视构图、或审核器个人偏好自行推导。

---

## 2.2 Full-slide Canvas Opacity Default

凡当前输出身份是**完整 PPT 页面（full-slide render）**，默认必须使用：

```text
OPAQUE_FULL_SLIDE = ON
```

该规则明确覆盖：

- 封面 / title slide；
- 章节页 / section divider；
- 普通内容页；
- 总结页 / 结束页；
- 任何将作为 `candidate`、Anchor 候选或 `Approved Slide Render` 的完整 16:9 PPT 页面。

完整页面必须在整个画布范围内拥有确定的不透明背景。背景可以是纯白、浅灰、纯色、渐变、大面积留白或极简背景；**白色背景 / 留白不等于透明背景**，不得为了“避免透明”强迫增加纹理、装饰或复杂背景。

透明背景仅允许两类显式例外：

1. 用户明确要求该完整页面输出为透明背景；
2. 当前输出明确不是完整 PPT 页面，而是独立图形资产，例如 Logo、人物 cutout、图标、装饰元素或其他 `isolated graphic asset`。

独立透明素材不得直接冒充完整 `Approved Slide Render`。在没有上述显式例外时，不得因为模型偏好、PNG 格式、留白构图或“方便后续合成”自行生成透明 full-slide canvas。

# 3. Flat 2D Positive Definition

默认 `FLAT_2D` 要求页面第一视觉判断仍明显属于**二维、非照片化、非三维渲染**的插画、图解、线稿、信息图或平面设计语言。

允许二维元素使用有限的 **Illustrative Depth Cue** 来组织空间关系，例如：

- 重叠与遮挡；
- 远近大小的轻度变化；
- 斜向延伸；
- 浅层前后关系；
- 简化的空间方向；
- 建筑、山水或背景插画中的局部轻微透视线索；
- 不承担实体厚度塑造的轻微明暗与层次。

这些线索只能服务于二维插画表达，不能把主要对象或整页转换成 2.5D / Pseudo-3D / volumetric scene。

优先使用：

- 平面几何、二维图标、二维人物插画；
- 二维工程线稿、系统图、流程图、信息图与图表；
- 明显图形化、插画化的建筑 / 场景轮廓；
- 线、箭头、节点、平面标签；
- 轻微渐变与极轻阴影，仅用于层级而非实体体积。

`ZERO_PERSPECTIVE_2D` 是更严格的特殊模式。在该模式下，页面应采用正视 / elevation / flat symbol / planar diagram 表达，不使用明显透视缩短、可见顶面/侧壁、近大远小或景深式空间层次。

关键区别：

> `FLAT_2D` 禁止的是三维视觉机制成为主要表达方式；它不禁止正常二维插画中一切空间线索。

---

# 4. Flat 2D Forbidden Set

在默认 `FLAT_2D` 下明确禁止：

- Isometric / 等距插画作为主要空间机制；
- Axonometric / 轴测结构；
- 2.5D；
- Pseudo-3D / 伪3D；
- 3D-rendered scene；
- 主要对象依靠可见顶面 + 侧面 + 厚度来建立实体体积；
- 通过椭圆、连续侧壁、上下表面模拟圆柱体体积；
- 挤出、浮雕、斜角（bevel）文字或图标；
- 系统性相机透视、真实材质、空间光照和体积阴影共同建立的三维场景；
- 虽由二维矢量绘制，但整体第一视觉判断明显在模拟三维实体或三维空间的场景。

以下现象在 `FLAT_2D` 下**不得单独视为违规**：

- 一条斜线或斜向延伸；
- 局部遮挡；
- 轻微远近关系；
- 低对比背景建筑 / 山体 / 城墙的浅空间层次；
- 为二维插画叙事服务的局部、非主导透视；
- 简化顶部或侧面的轮廓暗示，只要没有被系统性用于塑造实体厚度。

判定依据是：

> 最终视觉是否**系统性地以三维空间或实体体积作为主要表现机制**。

不是：

> 是否能在局部找到任何透视、顶部、侧面或远近线索。

当且仅当当前模式明确为 `ZERO_PERSPECTIVE_2D` 时，明显透视、近大远小、可见顶面/侧壁和景深式层次本身才可以作为模式违规。

# 5. Non-Photographic Rendering Boundary

主视觉必须优先采用：

- 二维扁平插画；
- 二维工程线稿；
- 平面图解；
- 几何构成；
- 图标与符号；
- 二维信息图；
- 正视或平面的建筑 / 设备抽象；
- 清晰的二维关系图与数据视觉化。

明确避免：

- 照片或摄影素材作为主视觉；
- Stock-photo / 素材图库式构图；
- Photo collage / 照片拼贴；
- Photorealistic / 拟真照片风渲染；
- Camera-like lighting / 摄影棚式或电影式真实布光；
- Depth of field / 景深虚化；
- Lens flare / 镜头光晕；
- 真实材质质感，如玻璃、金属、混凝土、皮革等被写实呈现；
- 通过高光、反射、纹理、噪点和环境光模拟真实摄影对象；
- “一张写实场景图 + 少量文字 / 几何装饰”的广告海报式页面。

允许：

- 明确非摄影化的编辑插画；
- 复杂、专业的二维插画与工程细节；
- 多层但仍处于同一信息平面的二维图形组织；
- 轻微、平面的图形纹理；
- 轻微印刷颗粒或抽象纹理，只要不模拟真实材质与摄影质感；
- 具有专业细节的二维技术图，只要它仍明显属于图解而不是照片。

> **Non-photographic does not mean visually poor, generic, icon-only or low-detail.**

判据：

> 第一眼应被识别为“设计出来的二维图形 / 图解”，而不是“拍摄出来的场景”或“逼真渲染出来的照片”。

## 5.1 建筑、园区与工业场景特别规则

建筑、楼宇、厂房、园区、变电站、机房、城墙和山体是高风险对象，但不能因为存在空间关系就自动否决。

在默认 `FLAT_2D` 下允许：

- 正视二维轮廓、平面符号、二维工程线稿、平面剪影；
- 抽象几何化建筑语言；
- 低对比、背景性的二维建筑 / 城墙 / 山体插画；
- 为表达延伸关系而使用轻微斜向、遮挡、远近或局部透视，只要整体仍明显是二维插画。

应避免并按 H2 审核：

- 等距 / 轴测建筑群；
- 依靠连续顶面、侧壁和阴影塑造体积的楼群；
- 具有真实窗面、反射、材质、环境光和相机透视的场景；
- 让建筑/园区成为主要三维空间体验的 2.5D / Pseudo-3D 场景；
- 具有摄影景深或电影布光的园区 / 厂区场景。

**Canonical Regression Pattern — minor illustrative depth cue：** 低对比、小面积、图形化的背景对象即使存在轻微斜向延伸、局部顶部/侧面暗示，只要整体仍明显属于二维装饰插画，在 `FLAT_2D` 下应 `PASS`，不得仅以“存在透视”为由判 H2。若当前模式明确为 `ZERO_PERSPECTIVE_2D`，则可要求**仅对违规局部平面化**，不得无理由删除其他已成立的合法装饰。

如果建筑只能通过写实照片感或真正伪3D场景成立：

> RE-PLAN。

# 6. Perspective & Volume Guard

空间线索分为两个等级，不得混淆。

## Level 1 — Illustrative Depth Cue

以下通常属于二维插画的正常表达，在 `FLAT_2D` 下不得单独触发 H2：

- 遮挡；
- 轻微近大远小；
- 斜向延伸；
- 简化的前后层次；
- 低对比背景对象的浅空间关系；
- 局部顶部/侧面轮廓暗示，但没有连续厚度、真实材质或体积光影。

## Level 2 — Volumetric / Spatial Simulation

以下属于需要阻止的三维视觉机制：

- 连续消失关系或强相机透视组织主要场景；
- 主要对象依靠顶面、侧壁和厚度才能成立；
- Isometric / Axonometric / 2.5D；
- 对象通过体积阴影、真实材质、高光或环境光被塑造成实体；
- 页面形成明显房间、厂区、城市、设备阵列等三维空间体验；
- 第一眼明显被识别为 2.5D / Pseudo-3D / 3D-like scene，而不是二维插画。

`FLAT_2D` 只禁止 Level 2。

`ZERO_PERSPECTIVE_2D` 同时限制明显 Level 1 空间线索；但该模式必须有显式上游冻结依据。

审核器不得以“发现一处透视线索”直接跳到 H2，必须先判断它究竟是 Illustrative Depth Cue，还是已经构成 Volumetric / Spatial Simulation。

---

# 7. Violation-triggered Rendering Fallback

二维 / 非照片化替代表达只能在**具体视觉方案已经出现违规风险时**触发。

不得因为主题词自动触发固定符号。

例如：

```text
AI
≠ 自动使用芯片

电力
≠ 自动使用杆塔

数据中心
≠ 自动使用服务器机柜
```

如果模型已经提出合法的二维抽象表达：

> 保留，不替换。

只有违规时，才对违规对象做局部二维化或非照片化处理，并优先保留上游已选视觉媒介；跨媒介替换只在原媒介无法合法保留时使用。

## 7.1 违规类型 → 合法化方向

| 违规视觉 | 优先二维化方向 |
|---|---|
| 立体设备 | 正视二维轮廓、平面技术符号、二维工程线稿 |
| 等距建筑 | 正视建筑轮廓、平面建筑符号 |
| 透视房间 / 控制室 | 平面功能模块、正视显示界面、二维关系图 |
| 3D 数据中心 | 平面节点网络、正视设备符号、二维系统关系 |
| 圆柱体 | 正视符号、简化平面轮廓；不保留顶面与侧壁 |
| 三维能量流 | 平面箭头、线、节点、二维流向关系 |
| 立体场景拼装 | 平面信息图、二维图解组合或关系图 |
| 照片感人物 / 建筑 / 设备 | 扁平插画、正视线稿、平面剪影或抽象几何表达 |
| 写实工业 / 城市场景 | 拆解为二维对象、平面关系与图解化背景，不保留摄影场景感 |

原则：

> Replace only the violating visual interpretation, not the underlying semantics.

---

# 8. Gradient Guard

允许：

- 背景极浅渐变；
- 同一平面色块中的轻微色差；
- 为层级提供的弱渐变。

禁止：

- 球体式中心高光；
- 金属感渐变；
- 圆柱体明暗；
- 通过明暗让对象鼓起或凹陷；
- 用渐变塑造实体体积。

原则：

> Gradient may support hierarchy, but must not create volume.

---

# 9. Shadow Guard

允许极轻阴影，仅用于：

- 平面信息层分离；
- 浅背景下提高容器边界辨识；
- 非物理性的轻微层级提示。

禁止：

- 明显落地阴影；
- 强方向性投影；
- 大面积模糊阴影；
- 卡片明显悬浮；
- 使用阴影表现物体厚度；
- 使用阴影把设备塑造成实体；
- 明显长阴影（long shadow）制造空间方向或实体感。

原则：

> Shadow may separate flat layers, but must not place objects in physical space.

---

# 10. Container & Glass Guard

允许：

- 平面色块；
- 细边框；
- 轻微色差；
- 极轻层级阴影；
- 极弱透明平面用于分区。

禁止：

- 厚卡片；
- 多层悬浮面板；
- 手机 UI 式立体浮层；
- 强 Glassmorphism；
- 玻璃高光；
- 玻璃厚度；
- 发光透明边；
- 大量悬浮玻璃面板。

默认：

```text
GLASSMORPHISM = OFF
```

---

# 11. HUD / Glow / Neon Guard

默认：

```text
HUD_DECORATION = OFF
GLOW = OFF
NEON = OFF
SCI_FI_COCKPIT_UI = OFF
```

禁止：

- 高饱和强外发光；
- 发光节点；
- 发光连线；
- 发光文字；
- 发光边框；
- 雷达扫描圈；
- 扫描线；
- 瞄准框；
- 无意义技术刻度；
- 游戏 HUD；
- 科幻驾驶舱界面；
- “黑底 + 强发光 + 满屏科技线”的通用科幻科技模板。

当科技感、工程感或专业感属于当前上游设计目标时，应由**上游已选视觉媒介自身**的结构、节奏、专业细节、信息关系与二维视觉语言建立，不预设节点、连线、线稿或几何构成为通用答案。插画、数据视觉、图解、编辑型图形或其他合法二维媒介都可以用各自的语言表达技术气质。

判据：

> 如果去掉 Glow、HUD、Neon 后页面就失去科技感，说明当前已选视觉媒介中的科技视觉语言本身设计失败，应在生成前重新规划；不得仅因此自动改写成节点网络、技术线稿或其他 diagrammatic safe solution。

# 12. Current Generation Plan Rendering Legalization

在真正生图之前，只检查“当前视觉计划是否同时满足当前二维渲染模式与非照片化渲染边界”。

不得借渲染合法化重新改变页面设计思想。

> **Rendering legalization must preserve the upstream-selected primary visual carrier and expressive mechanism.**

不得借“合法化”重新选择视觉媒介。若上游选定的是合法二维插画、编辑型插画或其他非图解型二维表达，不得仅因为 diagram、line art、icons、nodes 或 geometric information graphics 更容易保持 Flat 2D，就把原方案改写为这些形式；反之，上游已经选定流程图、系统图、数据视觉或其他图解型表达时，也不得为了“鼓励插画”而擅自加入人物、场景或叙事性插画。

若上游视觉媒介本身合法，仅局部对象或空间机制越界，应优先在**原媒介内部**做最小二维化 / 非照片化修正。只有原媒介无法在不破坏语义和设计概念的情况下合法保留时，才允许返回上游 RE-PLAN，而不是由本协议自行改选另一种媒介。

检查：

1. 页面第一视觉判断是否仍明显属于二维、非照片化表达；
2. 主要对象是否系统性依赖实体厚度、Isometric / Axonometric / 2.5D / Pseudo-3D 才能成立；
3. 当前构图是否把相机透视或三维空间作为主要视觉机制，而不仅是局部 Illustrative Depth Cue；
4. 科技感是否依赖 HUD / Glow；
5. 渐变和阴影是否仅承担层级；
6. 主视觉是否呈现明显照片感、摄影素材感或拟真渲染；
7. 建筑 / 园区 / 工业对象是否保持图形化二维插画语言，而不是写实或伪3D场景；
8. 当前输出若为完整 PPT 页面（包括封面），是否保持 `OPAQUE_FULL_SLIDE`，不存在未经明确授权的透明画布；
9. 如存在违规对象，能否只局部替换为二维、非照片化表达而保持原设计概念。

如果无法在不破坏设计概念和语义的情况下满足当前二维模式与非照片化表达：

> RE-PLAN。

```text

For every full PowerPoint slide — including the cover/title slide — render a complete 16:9
OPAQUE_FULL_SLIDE canvas with an opaque background across the entire frame.

editorial illustration, diagrammatic graphics, information design, technical line art,
data visualization, flat geometric composition, or another valid 2D visual language.
Do not substitute one of these media for another merely because it is easier to keep flat.

Limited illustrative overlap, near/far layering or mild perspective cues are allowed

If a local object violates the 2D boundary, correct that local rendering mechanism first
```

# 17. Post-generation Qualification Review

生成后的审核只做**资格判定（qualification review）**。它不是第二轮视觉探索，也不是无限寻找更优图片的优化器。

## 17.1 Candidate 不是 Approved Render

每次真实生图结果首先只能登记为 `candidate`。候选必须绑定当前有效 Stage 2 run 与稳定 `page_id`；普通文件路径、调试文件或非图像资产不能因为被登记就自动获得正式页面地位。

推荐最小状态：

```text
candidate
   ↓ review
PASS      REVISE      REJECT
 │           │            │
 │           └→ targeted new candidate
 │
 └→ current approved render
```

`Approved Render` 是审核 PASS 的结果，不是文件类型，也不得通过直接登记路径绕过审核。唯一的非晋级例外是《PPT视觉探索与Anchor延续协议》定义的 Anchor 自由探索：`approval_mode = anchor_exploration_candidate` 的 PASS 只形成 `qualified` Anchor candidate，使多个合格构图能在用户选择前同时存在；用户从正式 Anchor Formal Candidate Set 中选中后，才以 `user_selected_anchor_page` 晋级为 current Approved Render。普通页面 PASS 行为不变。

## 17.2 四类 Hard Gate

只有以下四类问题可以阻止候选通过。

### H1 — CORE_SEMANTIC_CONFLICT

页面的核心视觉表达与当前批准语义发生实质冲突，例如：

- 核心对象或强制信息缺失；
- 并列、因果、层级、时间、流程、定量等关系被错误表达；
- 页面主题或核心结论明显跑偏；
- 主要视觉结构传达了材料和批准语义不支持的事实。

**局部内容边界：** 偶发的局部内容或附加表达，如果没有对核心语义造成实质冲突，不因其自身自动构成 H1；如果局部错误本身已经成为主要事实主张，则仍可 H1。具体文字清除、真值恢复与图形化文字处理继续由 Stage 3 相关协议负责。

### H2 — FROZEN_VISUAL_CONSTRAINT_VIOLATION

`NON_COVER` 指除封面 / Cover 之外的全部正式 PPT 页面；用户明确例外要求可以来自当前具体页面的明确展示性文字要求，也可以来自明确的 poster / promotional / display-oriented communication task，二者均可形成当前页面的展示性 Typography carrier 授权。该授权只允许 Typography 成为候选 `primary_visual_carrier`，不要求 Typography-first，也不改变 mandatory information、semantic relation 或其他 Hard Gate。

页面**明确且实质性违反**已经冻结的视觉边界或用户已确认的视觉规则，例如：

- 明显 Isometric / Axonometric / 2.5D / Pseudo-3D，或以实体厚度、三维空间模拟为主要视觉机制；
- 明显照片感 / 摄影素材感 / 拟真材质；
- 完整 PPT 页面（包括封面）在没有显式透明例外时使用透明背景或透明画布；
- 明确禁止的 HUD / Glow / Neon；
- 与当前 Anchor Family 发生实质视觉媒介漂移；
- `NON_COVER` 页面在无当前页面明确展示性文字要求、且无 poster / promotional / display-oriented communication task 页面级授权时，以展示性大字号标题或其他标题文字成为页面第一视觉焦点、主要构图主体或实际 `primary_visual_carrier`，使页面由标题而非实质信息内容主导。

Anchor Family 漂移只检查 Family-level 视觉语言：色彩体系、二维/非照片化媒介、线条与几何语言、抽象程度、总体视觉气质。

以下差异本身**不是** H2：人物长相或动作不同、人物局部画法变化、图标不同、当前页构图不同、因当前语义产生的新视觉载体。`NON_COVER` 页面保留清晰且明显高于正文的正常标题层级也不属于 H2；只有标题已经越过标题/导航角色，实际成为页面主视觉时，才适用上述大标题边界。

当当前页面已有 poster / promotional / display-oriented communication task 页面级授权时，不得仅因展示性 Typography 成为第一视觉焦点而自动判定 H2；仍必须检查 mandatory information 是否完整、语义关系是否正确，以及其他 H1–H4 是否真实成立。该授权不强迫页面采用 Typography-first，插画、图解、结构或其他合法 carrier 仍可按当前语义择优。

只有当页面在色彩体系、二维/非照片化媒介、线条与几何语言、抽象程度、总体视觉气质等方面发生**实质性 Family 漂移**时，才构成 Style DNA 违规。若以 Anchor 漂移作为 H2 证据，审核记录必须能够指出至少一项当前有效 `Anchor Style DNA` 特征被实质违背；不能仅以“看起来和 A 不一样”举证。

在默认 `FLAT_2D` 下，局部轻微透视、遮挡、远近或背景建筑的浅空间关系本身不是 H2。若以二维边界作为 H2 证据，`observable_evidence` 必须说明该现象为什么已经**实质跨越**为 Isometric / Axonometric / 2.5D / Pseudo-3D / volumetric scene，而不能只写“存在透视”“看到了侧面”。

透明 full-slide 的 H2 修订必须保持已有构图、文字布局、插画、色彩和视觉风格，只把完整页面背景恢复为不透明画布；不得因为透明问题重新设计整页。封面与内容页适用同一规则。

Canonical Regression Patterns：

- **opaque full-slide**：完整页面未要求透明，但生成为透明背景 → `H2`；保留构图，仅恢复不透明完整画布。
- **opaque whitespace**：页面使用纯白 / 浅色大留白且像素背景不透明 → `PASS`，不得误判为透明。
- **isolated transparent asset**：用户明确生成透明 Logo / cutout / 图标等独立素材 → 允许，但该素材不是完整 Approved Slide Render。
- **minor illustrative depth cue**：低对比、小面积二维背景对象存在轻微斜向延伸和浅空间线索，整体仍明显为 Flat Illustration → `FLAT_2D: PASS`。
- **volumetric primary object**：主视觉对象依靠明显顶面 / 侧壁 / 厚度 / 体积阴影成立 → `FLAT_2D: H2`；定向修订只平面化违规对象。
- **whole-page isometric / axonometric spatial mechanism**：整页以 Isometric / Axonometric 空间为主要表达 → `H2`。
- **explicit zero-perspective mode**：若当前模式明确为 `ZERO_PERSPECTIVE_2D`，明显 Level 1 空间线索可判 `H2`，但只对违规局部做平面化。
- **NON_COVER heading as primary carrier**：标题成为第一视觉焦点并占据主要构图空间、实质信息被压缩为次要区域，且用户无明确例外要求 → `H2`。
- **NON_COVER normal heading hierarchy**：标题明显高于正文，但主体区域仍由实质信息承担，标题不主导页面 → `PASS`。
- **explicit poster / promotional task**：当前页面明确承担 poster / promotional / display-oriented communication task，展示性 Typography 成为第一视觉焦点 → 不得仅据此 H2；继续按 mandatory information、语义关系及其他 Hard Gate 审核，且不强迫 Typography-first。

### H3 — RENDER_INTEGRITY_FAILURE

页面存在客观的渲染/可读性故障，使其无法作为正式页面使用，例如：

- 大面积元素畸变、裁切或异常；
- 核心元素严重遮挡；
- 关键视觉无法辨识；
- 信息密度已经实际造成核心层级无法区分、关键内容不可读或主要结构互相冲突。

“信息量有点高”“感觉稍满”“留白还可以更舒服”本身不是 H3。只有能够指出具体可观察的不可读、遮挡、层级崩坏或结构冲突时，才可阻止通过。若经过 Stage 2 合理重组、压缩与视觉化后仍不可读，则按《Stage1至Stage2语义接口协议》的 `Irreducible Content Overload` 边界返回 Stage 1，而不是无限重生图片。

### H4 — STAGE3_HANDOFF_BLOCKER

页面虽然可能表面可看，但当前已经能够确认存在 Render / Content Truth 交接矛盾，使 Stage 3 无法在不明显破坏设计的情况下完成正式文字恢复，例如：

- 未批准的大块 Raster 文字已经成为主体构图，删除后会明显破坏视觉平衡；
- 关键文字与复杂主体深度融合，无法可靠清除和恢复。

普通小标题、角标、装饰字、收束句、零碎错字或可局部清除的多余文字不属于 H4。

H4 不得仅因为“这个页面理论上可能不好被 Magic Layers 拆层”提前否决视觉更好的页面；非文字对象的实际拆层质量仍以 Stage 3 真实处理结果为准。若 Stage 3 后续以实际结构失败证据返回 Stage 2，则该证据可重新打开当前页面。

## 17.3 Soft Preference 不得触发返工

以下内容默认只能记录为 `review_notes`，不得单独或累计触发 `REVISE / REJECT`：

- 人物造型还可以更统一；
- 局部图标还可以更精致；
- 留白还可以更舒服；
- 色彩还可以进一步协调；
- 构图还有理论优化空间；
- 信息量“感觉稍高”但实际可读；
- 页面还可以更“高级”；
- 非核心文案不够准确；
- 存在可由 Stage 3 清除的多余文字；
- 与 Anchor 存在局部对象差异但整体 Family 未漂移。

多个 Soft Preference 不能通过数量累加自动升级成 Hard Failure。只有当其最终造成 H1–H4 中某一项可观察失败时，才允许阻止通过。

## 17.4 PASS 默认与否决举证

审核顺序：

```text
Candidate
  ↓
Check H1–H4
  ↓
No evidenced Hard Failure
  ↓
PASS
```

任何 `REVISE / REJECT` 至少必须记录：

```yaml
review_record:
  verdict: REVISE | REJECT
  failed_hard_gate: H1 | H2 | H3 | H4
  observable_evidence:
  required_correction:
  review_notes: []
```

`failed_hard_gate` 记录当前 verdict 的 primary Hard Gate；其他同时存在的问题写入 `observable_evidence` 或 `review_notes`，不建立第二套多 gate schema。

“还不够高级”“可以再优化”“感觉不统一”“信息有点多”等不可验证表述不能成为 `failed_hard_gate`。

PASS 可以附带 `review_notes`，但 Notes 不影响候选升级为 current approved render。

## 17.5 PASS 后停止自动生成

候选一旦 PASS：

```text
PASS
→ current approved render
→ STOP automatic generation for this page
```

不得因为模型认为“也许还能更好”而继续自动生图。

如果用户明确要求“再试一版 / 再给一个方案”，可以生成新的候选，但旧 current approved render 必须保留，直到新候选也 PASS 后才将旧版标为 `superseded`。新候选若 REVISE / REJECT，旧 approved render 仍为 current。

## 17.6 REVISE 必须是 targeted revision

`REVISE` 必须针对 Hard Failure 形成明确 correction delta。下一次生成应优先保持已经成立的页面结构、构图和视觉部分，只修改必要失败项。

**任何局部 Hard Failure，只要主要有效设计仍可合理保留，都优先 targeted revision；不得仅因 Gate 类型扩大 correction scope。**

例如：

```text
H2: 局部主对象出现明显实体厚度
→ 保持其余构图与配色不变
→ 仅把违规对象改成正视、扁平二维图形
```

不得因一个局部违规无理由推翻整页；除非其他对象各自存在独立 Hard Failure，不得扩大 correction scope。

不设置机械的总生成次数上限，但禁止**无变化重试**：如果无法提出新的 correction delta，或只是以相同理由重复同一生成条件，则停止自动重生并报告当前页 unresolved，而不是继续消耗生成次数。

## 17.7 REJECT 的边界

`REJECT` 表示当前 Candidate 本身不再作为定向修订基础，应回到 Visual Plan / Candidate 重新选择视觉解。

`REJECT` 必须比 `REVISE` 多提供一项 `replan_evidence`，回答：**为什么 targeted revision 已不是合理恢复路径？** 只有当 Hard Failure 需要改变主要视觉结构、当前 Candidate 已无法通过局部修正合理恢复，或多个结构性 Hard Failure 共同使当前 Candidate 不再适合作为修订基础时使用。

可接受的 `replan_evidence` 包括：主要视觉结构本身编码错误关系；修复必须改变主要视觉结构；多个结构性 Hard Failure 的组合效应；或真实 targeted revision 结果已经证明主要结构无法合理保留。

“重做更稳”“风险比较大”“感觉不够好”“简单一点更容易过”“还能重新设计得更漂亮”等不能作为 `replan_evidence`。

若 `required_correction` 明确表示“只需局部修改，其他主体设计可保留”，则除非 `replan_evidence` 另行证明该局部修正为什么不足，否则不得 `REJECT`。

`REJECT` 不能作为“我个人不太喜欢这张”的审美标签。

## 17.8 用户明确视觉接受的权威

当候选不存在 H1–H4 时，用户明确表示“这张就用 / 很好 / 采用这一版”，应直接确认或维持 PASS；模型不得以 Soft Preference 继续自动生成。

如果候选仍存在 H1–H4，应明确指出具体冲突。只有用户明确修改对应语义要求、冻结视觉约束或正式交付条件后，才能基于新约束重新判断；不得悄悄忽略 Hard Failure。

## 17.9 Stage 2 run 与已通过状态不得被重复启动清零

在批准大纲、页面集合与 Anchor / 全局渲染约束未发生实质变化时，重复进入 Stage 2 应恢复既有当前 run 和页面状态，不得把已经 PASS 的页面、Candidate 历史或当前 approved render 悄悄清零。

确需建立新 run 时，应明确由以下事件触发：

- 当前批准大纲发生变化；
- 用户明确改变全局 Anchor / Style DNA 或冻结视觉约束；
- 用户明确要求重新开始 Stage 2。

旧 run 可以归档用于追溯，但不得与新 run 的 current 状态混用。仅某一页的候选修订不得清空其他仍 current 的通过页。

## 17.10 Qualification Authority

Post-generation qualification is fully defined by H1–H4 and the disposition rules above; no additional summary gate exists.

---

# 18. 不允许本协议越权

本协议不得：

- 把并列信息改成流程；
- 为页面新增系统层级；
- 因为“二维更好画”而删除必要信息；
- 把所有技术对象固定映射为某个图标；
- 把所有页面改成同一种卡片结构；
- 因为防止 3D 或照片感而降低页面的专业性与信息量；
- 因为“非照片化”而把所有复杂对象粗暴替换成通用图标；
- 修改用户已选择的 Anchor Style DNA。

如果当前二维渲染模式或非照片化边界与当前设计概念冲突：

> 返回上游重新规划。

---

# 19. 最终原则

```text
Plan before rendering.
Describe the desired Flat-2D / current-mode, non-photographic solution positively.
Use negative boundaries as guardrails.
Legalize only actual violations.
Preserve semantic and design intent.
Generate only after Preflight passes.
Review for qualification, not theoretical perfection.
PASS when no evidenced Hard Failure exists.
Stop automatic generation after PASS.
```

中文：

> **先规划，再生图；默认采用 Flat 2D、非照片化视觉语言，允许正常二维插画的有限空间表达，只阻止真正的三维视觉机制；仅在上游明确要求时启用 Zero-Perspective；只修正真实且实质的违规，不用渲染协议替代创意设计；生成后只做资格审核，没有可举证 Hard Failure 就应通过，PASS 后停止自动重生。**


## Runtime dispatch: Candidate review, formal display and handoff

Every generated page image begins as a Candidate: `stage2-candidate-register --slide-id <id> --artifact <image> --generation-intent <delta>`. Review it with `stage2-candidate-review`. Stage 2 review is a **qualification gate, not an unbounded optimization loop**: in the absence of an evidenced H1–H4 Hard Failure the verdict is PASS; aesthetic preferences such as “could be more polished”, local character variation, removable incidental text, or readable information density belong only in review notes. An evidenced Hard Failure with a credible targeted correction is `REVISE`. `REJECT` is allowed only when the review additionally provides `--replan-evidence <evidence>` showing why targeted revision is not a reasonable recovery path. After `REJECT`, return to reference 03 for neutral re-planning under all still-valid page requirements. If the evidence required for a disposition cannot be established, do not fabricate that verdict. PASS promotes that Candidate to the page's single current Approved Render and stops automatic generation for that page. Generate another version after PASS only when the user explicitly requests one (`--user-requested-variant`); keep the old PASS current until a replacement also PASSes. Repeating the same failed `REVISE` generation intent without a new corrective delta is blocked.

After `stage2-visual-status` becomes COMPLETE, do **not** enter Stage 3. Run `stage2-formal-display --state <state>` and formally show exactly the returned ordered `renders` set to the user. This set is derived only from each page's current Approved Render, so a locked cover/Anchor page must appear even if it was not regenerated in the latest batch; never reconstruct the formal display from recent image-tool outputs, folders, or Candidate History. STOP at `AWAITING_USER_VISUAL_APPROVAL`. When the user's contextual intent unambiguously accepts that exact displayed set, record it with the structured `stage2-visual-approve --state <state> --message <actual-user-reply>` action; Runtime validates the displayed fingerprint and does not keyword-match the reply again. If the user asks to revise selected pages, write the requested slide IDs as a JSON array and call `stage2-visual-revise --state <state> --slide-ids-json <file>`; only those pages reopen, while all other current PASS pages remain current. Any current Approved Render change invalidates the prior visual approval and requires a new complete formal display and user confirmation.

All full-slide ImageGen renders — **including the cover/title slide** as well as section, content, summary and closing slides — default to a complete opaque 16:9 canvas under reference 04 (`OPAQUE_FULL_SLIDE`). White, light, solid-color, gradient and intentionally minimal backgrounds are valid opaque backgrounds. Transparent full-slide output is allowed only when the user explicitly requests it; transparent isolated assets (Logo/cutout/icon/decorative graphics) remain allowed but are not themselves Approved Slide Renders.

After each current Approved Render exists, register `final_content_truth:<slide_id>` with `stage2-artifact-register`, then mark `stage2-text-reconciled --slide-id <id>`. `stage2-handoff-status` must be COMPLETE before Stage 3. Incidental wrong raster text or removable extra text does not by itself force page regeneration when core semantics remain correct and Stage 3 can remove/restore it. If the Outline changes, previous Stage 2 results remain history only and cannot become current. A blocked Stage 1 gate means STOP and show the current Outline for review. The user's acceptance applies only to the exact Outline presented in the current review interaction.
